<h1 align="center">Keith</h1>

<p align="center">
  <strong>Первый агент, который действительно эволюционирует — не за счёт трюков с промптами, а изменяя, тестируя и безопасно продвигая правки в собственную обвязку (harness).</strong>
</p>

<p align="center">
  Keith превращает реальный опыт в изменения той машины, которая определяет, как он
  рассуждает, выбирает инструменты, управляет контекстом и доводит работу до конца —
  а не в ещё одну заметку в промпте. Каждая новая версия собирается в изоляции,
  тестируется против текущего Keith и принимается только если показывает себя лучше
  и не нарушает ваши границы безопасности.
</p>

## Попробовать

Самый короткий путь — Docker:

```bash
cp .env.example .env
# Укажите KEITH_WEB_LOGIN_SECRET и один ключ провайдера моделей в .env.
docker compose up --build
```

Откройте <http://localhost:7341>. Keith хранит состояние в томе `keith-data`
и может работать внутри текущего рабочего дерева по пути `/workspace`.

Разрабатываете из исходников вместо этого?

```bash
./keith doctor
./keith setup
./keith dev
```

См. [руководство по установке](docs/installation.md) — там описаны TUI, настройка
провайдеров, обновления, резервное копирование и управление сервисами.

## Как Keith эволюционирует

Каждый запуск даёт Keith больше, чем просто журнал. Он формирует свидетельства
того, как отработал весь агент: путь рассуждений, выбор инструментов,
использование контекста, задержки, стоимость, восстановление и финальный результат.

Жёсткий сбой может вскрыть возможность для эволюции, но то же может сделать
и расточительный вызов инструмента, медленное восстановление или результат,
который мог бы быть лучше.

Keith превращает самую сильную возможность в проверяемую гипотезу, собирает
несколько кандидатов обвязки в стороне от работающей системы и сравнивает их
с текущей версией на работе, которую автор предложения не видел. Кандидат
проходит дальше только если даёт измеримое улучшение и не вносит регрессий.

```text
опыт → возможность → проверяемая гипотеза → кандидаты обвязки
     → отложенная оценка → канарейка → наблюдение → оставить или откатить
```

В этом и состоит главная ставка Keith: агент должен не просто делать работу.
У него должен быть безопасный, инспектируемый способ стать лучше в этой работе.

### Исправляй, пока он работает

Keith Computer — это видимый, изолированный рабочий стол. Смотрите за запуском
в реальном времени, одним действием заберите клавиатуру и указатель, исправьте
проблему и верните управление. Эксклюзивная аренда управления не даёт вам
и Keith бороться за один и тот же экран.

### Учи работе, а не ещё одному промпту

Когда вы показываете задачу, Keith записывает полезную структуру за ней:
состояние экрана, действия клавиатуры и указателя, цели в UI, контекст
приложения, тайминги, нарратив, файлы, активность буфера обмена и каждую
передачу управления. Он превращает эти свидетельства в редактируемый
**TaskRecipe** с входами, контрольными точками, шагами подтверждения,
восстановлением, версиями и откатом.

Вы даёте Keith не просто запись экрана. Вы показываете ему фрагмент работы,
который он может воспроизвести и улучшить.

### Пусть чинит обвязку, а не правила

Самовосстановление полезно, только если кандидат не может сдвинуть флажки.
Кандидаты на правку в Keith не могут редактировать судью, отложенные тестовые
случаи, учётные данные, то, что Keith может помнить или раскрывать, ваши
правила подтверждения, проверки релиза, шлюз продвижения или путь отката.

Выберите, как далеко Keith может зайти:

- **Только совет**   объяснить предложенную правку и подождать.
- **Теневое тестирование**   собрать и протестировать кандидатов, но не продвигать.
- **Автономное восстановление**   канарейка, наблюдение и откат в заданных вами пределах.

В каждом режиме защищённые правила остаются вне досягаемости кандидата.

### Один Keith, а не папка с ботами

Web UI, TUI, OpenAI-совместимый API, нативный API, ACP-клиенты, каналы
мессенджеров, подключённые приложения и компьютер — все обращаются к одному
агенту под управлением демона. Профильные воркеры могут исследовать, писать
код или работать с инструментами за кулисами, не превращая продукт
в дашборд с личностями, которыми нужно управлять.

Сессии переживают отключения клиентов. Обязательства, ожидания, запланированная
работа, цели и активные запуски могут восстанавливаться после рестарта.
Начните в терминале, проверьте результат из Slack, завершите в браузере —
без трёх несвязанных ассистентов.

## Что можно делать с Keith

| Вы хотите… | Keith может… |
| --- | --- |
| Передать задачу в браузере или на рабочем столе | Работать в видимом или скрытом компьютере, пока вы смотрите, делаете паузу или перехватываете управление |
| Научить повторяемому процессу | Превратить живую демонстрацию в редактируемый, воспроизводимый TaskRecipe |
| Перестать повторять одну и ту же ошибку агента | Диагностировать обвязку, тестировать конкурирующие правки, выкатить победителя канарейкой и откатить |
| Использовать свои модели | Маршрутизировать профили через OpenAI, Anthropic, OpenRouter, Ollama или другого поддерживаемого провайдера |
| Обращаться к тому же агенту откуда угодно | Обслуживать Web, TUI, ACP, API, Discord, Slack, Telegram, WhatsApp, Teams, Google Chat, email и Matrix-клиентов |
| Подключать реальные сервисы | Использовать подключённые приложения с подтверждением, Composio, MCP-серверы и WASI-плагины с ограниченными возможностями |
| Строить поверх Keith | Использовать OpenAI-совместимый `/v1` API или типизированный нативный `/platform/v1` API |
| Запускать на своей инфраструктуре | Разворачивать через Docker, Kubernetes, Railway, Fly.io, DigitalOcean, Azure, AWS или Google Cloud |

## Один рантайм, много способов войти

```text
Web · TUI · OpenAI API · Platform API · ACP · каналы
                         │
                      agentd
              сессии · политика · восстановление
                         │
                 арендованные воркеры агента
                         │
       модели · инструменты · плагины · CUA · подключённые приложения
```

`agentd` владеет истиной. Клиенты лишь отображают его сессии и жизненный цикл,
а не изобретают собственное состояние. Воркеры выполняют ходы под арендой,
а доменные крейты держат политику отдельно от внешних адаптеров.

См. [гайд по крейтам](docs/crate-guide.md) и
[границы зависимостей](docs/architecture/dependency-boundaries.md) для полной
карты системы.

## API и расширения

Keith предоставляет две HTTP-поверхности:

- **OpenAI-совместимый `/v1`** для существующих SDK и инструментов вроде Open WebUI.
- **Нативный `/platform/v1`** для доверенных клиентов, которым нужны сессии
  Keith, жизненный цикл, подтверждения, артефакты и события в реальном времени.

Расширения могут работать как WASI-компоненты с ограниченными возможностями,
MCP-серверы, навыки или подключённые приложения с подтверждением. ACP-клиенты
могут подключаться через встроенный stdio-сервер. См.
[OpenAI-совместимость](docs/openai-compatibility.md) и
[интеграцию с платформой](docs/platform-integration.md).

## Безопасность

> [!WARNING]
> Keith может выполнять команды, менять файлы, управлять браузером и обращаться
> к внешним сервисам с теми полномочиями, которые вы ему дадите. Используйте
> рабочее пространство, которое можно проинспектировать и восстановить.
> Считайте вывод модели, сообщения в каналах, загруженные страницы, плагины,
> навыки, MCP-серверы и кандидатов на правку ненадёжными.

Держите Web UI и API на loopback, если только вы не добавите TLS, сильную
аутентификацию и явную сетевую политику. Используйте разные секреты для
входа в Web, API, провайдеров моделей и подписания релизов. Никогда не
публикуйте учётные данные или неотредактированные трассировки в публичном
issue.

Сообщайте об уязвимостях приватно через
[форму security advisory](https://github.com/Sidiora-Labs/keith-agent/security/advisories/new)
на GitHub. Прочтите [SECURITY.md](SECURITY.md) — там описаны модель доверия,
область применения и правила репортинга.

## Развёртывание

Keith поставляется как один stateful OCI-образ с поддержкой Docker Compose,
Kubernetes с Helm, Railway, Fly.io, DigitalOcean Kubernetes, Azure Kubernetes
Service, Amazon EKS и Google Kubernetes Engine Autopilot.

```bash
./keith deploy kubernetes --render
./keith deploy railway
./keith deploy fly --app my-keith
./keith deploy aws --cluster keith --region us-east-1
```

Облачные команды по умолчанию печатают план. Развёртывание меняет инфраструктуру
только если передать `--execute` и установить `KEITH_DEPLOY_APPROVED=YES`.
Прочтите полное [руководство по развёртыванию](docs/deployment.md) перед тем,
как открывать Keith наружу хоста.

## Разработка и расширение

Команда `./keith` — это точка входа для контрибьюторов: настройка, локальные
сервисы, проверки, тесты, релизные сборки, контейнерные образы, скаффолдинг
и планы развёртывания. Артефакты сборки Rust остаются за пределами рабочего
дерева.

```bash
./keith check
./keith test
./keith image keith-agent:dev
./keith scaffold plugin my-plugin
./keith scaffold skill my-skill
```

Требуются Rust 1.93, Node.js 22.22, Corepack и Git. Перед открытием pull request
прочтите [CONTRIBUTING.md](CONTRIBUTING.md) и укажите команды и реальные
пользовательские сценарии, которые вы действительно прогоняли.
