## جرّبه

أقصر طريق هو Docker:

```bash
cp .env.example .env
# عيّن KEITH_WEB_LOGIN_SECRET ومفتاحًا واحدًا لمزوّد نموذج في .env.
docker compose up --build
```

افتح <http://localhost:7341>. يحتفظ Keith بحالته في وحدة التخزين `keith-data`
ويمكنه العمل داخل مسار `/workspace` في الـ checkout الحالي.

تفضّل التطوير من المصدر؟

```bash
./keith doctor
./keith setup
./keith dev
```

راجع [دليل التثبيت](docs/installation.md) لمعرفة TUI، وإعداد المزوّدين،
والترقيات، والنسخ الاحتياطية، وإدارة الخدمة.

## كيف يتطوّر Keith

كل تشغيل يمنح Keith أكثر من نصّ سِجِلّ. يُنتج أدلّة حول كيفية عمل الوكيل
بكامله: مسار التفكير، واختيارات الأدوات، واستخدام السياق، وزمن الاستجابة،
والتكلفة، والاستعادة، والنتيجة النهائية.

قد يكشف الفشل الحاد عن فرصة للتطوّر، لكن استدعاء أداة مُسرِفًا، أو استعادة
بطيئة، أو نتيجة كان يمكن أن تكون أفضل — تفعل ذلك أيضًا.

يحوّل Keith أقوى فرصة إلى فرضية قابلة للاختبار، ويبني عدة آليات مرشّحة بعيدًا
عن النظام الحيّ، ويقارنها مع الإصدار الحالي على عملٍ لم يرَه من اقترح التعديل.
لا يتقدّم أيّ مرشّح إلا إذا حقّق تحسّنًا قابلًا للقياس دون أن يُدخل تراجعًا.

```text
تجربة ← فرصة ← فرضية قابلة للاختبار ← آليات مرشّحة
     ← تقييم محجوز ← canary ← مراقبة ← إبقاء أو تراجع
```

هذا هو الرهان المركزي وراء Keith: لا ينبغي للوكيل أن ينجز العمل فحسب، بل
ينبغي أن يمتلك طريقةً آمنةً وقابلةً للتدقيق ليصبح أفضل في إنجازه.

### صحّح الخطأ أثناء عمله

Keith Computer هو سطح مكتب مرئيّ ومعزول. شاهد التشغيل مباشرةً، واستلم لوحة
المفاتيح والمؤشّر بإجراء واحد، وأصلح المشكلة، ثم أعد التحكم. يمنع عقد تحكّم
حصريّ أن تتنازع أنت وKeith على الشاشة نفسها.

### علّمه العمل، لا prompt آخر

حين تعرض عليه مهمة، يسجّل Keith البنية المفيدة خلفها: حالة الشاشة، وإجراءات
لوحة المفاتيح والمؤشّر، وأهداف واجهة المستخدم، وسياق التطبيق، والتوقيت،
والسرد، والملفات، ونشاط الحافظة، وكل عملية تسليم تحكّم. يحوّل تلك الأدلّة إلى
**TaskRecipe** قابل للتعديل، يحتوي على مدخلات، ونقاط فحص، وموافقات، وخطوات
استعادة، وإصدارات، وتراجع.

أنت لا تعطي Keith تسجيلًا للشاشة فحسب — بل تعرض عليه قطعة عمل يمكنه إعادة
تشغيلها وتحسينها.

### دعه يُصلح الآلية، لا القواعد

لا تنفع الإصلاحات الذاتية إلا إذا لم يستطع المرشّح تحريك أعمدة المرمى. لا
يمكن لمرشّحي إصلاح Keith تعديل الحَكَم، أو حالات الاختبار المحجوزة، أو بيانات
الاعتماد، أو ما يجوز لـKeith تذكّره أو كشفه، أو قواعد الموافقة لديك، أو فحوصات
الإصدار، أو بوابة الترقية، أو مسار التراجع.

اختر إلى أي مدى يمكن لـKeith أن يذهب:

- **استشارة فقط**   يشرح الإصلاح المقترح وينتظر.
- **اختبار في الظل**   يبني ويختبر المرشّحين، لكن لا يرقّي أحدًا.
- **إصلاح ذاتي**   canary ومراقبة وتراجع ضمن الحدود التي تحدّدها.

في كل وضع، تبقى القواعد المحميّة بعيدًا عن متناول المرشّح.

### Keith واحد، لا مجلد من البوتات

تصل واجهة الويب، وTUI، وواجهة `/v1` المتوافقة مع OpenAI، والواجهة الأصلية،
وعملاء ACP، وقنوات المراسلة، والتطبيقات المتصلة، والكمبيوتر — جميعها إلى
الوكيل ذاته الذي يملكه البرنامج الخفي. يمكن للعمال المتخصّصين البحث
والبرمجة وتشغيل الأدوات خلف الكواليس دون أن يتحوّل المنتج إلى لوحة تحكّم
مليئة بالشخصيات التي يتعيّن عليك إدارتها.

تصمد الجلسات بعد انفصال العملاء. يمكن استعادة الالتزامات، والانتظارات،
والعمل المجدوَل، والأهداف، والتشغيلات النشطة بعد إعادة التشغيل. ابدأ من
الطرفيّة، وتابع من Slack، وأنهِ في المتصفّح — دون أن تُنشئ ثلاثة مساعدين
لا علاقة بينهم.

## ما الذي يمكنك فعله بـ Keith

| إذا أردت… | فـ Keith يستطيع… |
| --- | --- |
| إسناد مهمة متصفّح أو سطح مكتب | العمل في كمبيوتر مرئي أو غير مرئي بينما تشاهد أو توقف أو تستلم التحكّم |
| تعليم سير عمل قابلة للتكرار | تحويل عرض مباشر إلى TaskRecipe قابل للتعديل وإعادة التشغيل |
| التوقّف عن تكرار فشل الوكيل ذاته | تشخيص الآلية، واختبار إصلاحات متنافسة، وتجريب الفائز بـcanary، والتراجع |
| استخدام نماذجك الخاصة | توجيه الملفات التعريفية عبر OpenAI أو Anthropic أو OpenRouter أو Ollama أو مزوّد مدعوم آخر |
| الوصول إلى الوكيل ذاته من أيّ مكان | خدمة عملاء Web وTUI وACP وAPI وDiscord وSlack وTelegram وWhatsApp وTeams وGoogle Chat والبريد وMatrix |
| ربط خدمات حقيقية | استخدام تطبيقات متصلة بموافقات، وComposio، وخوادم MCP، وإضافات WASI بنطاق قدرات |
| البناء فوق Keith | استخدام واجهة `/v1` المتوافقة مع OpenAI أو واجهة `/platform/v1` الأصلية والمُنمّطة |
| تشغيله على بنيتك التحتية | النشر عبر Docker أو Kubernetes أو Railway أو Fly.io أو DigitalOcean أو Azure أو AWS أو Google Cloud |

## وقت تشغيل واحد، ومداخل متعدّدة

```text
Web · TUI · OpenAI API · Platform API · ACP · قنوات
                         │
                      agentd
              جلسات · سياسة · استعادة
                         │
            عمال وكيل بعقد تحكّم
                         │
   نماذج · أدوات · إضافات · CUA · تطبيقات متّصلة
```

يملك `agentd` الحقيقة. يكتفي العملاء بعرض جلساته ودورة حياته، بدلًا من اختراع
حالة خاصّة بهم. ينفّذ العمال الأدوار تحت عقود تحكّم، وتبقي الـcrates
المجاليّة السياسة منفصلة عن المهايئات الخارجية.

اقرأ [دليل الـcrates](docs/crate-guide.md) و
[حدود الاعتماديّات](docs/architecture/dependency-boundaries.md) للحصول
على الخريطة الكاملة للنظام.

## واجهات API والامتدادات

يقدّم Keith سطحين عبر HTTP:

- **`/v1` متوافق مع OpenAI** لحزم SDK والأدوات القائمة مثل Open WebUI.
- **`/platform/v1` أصلي** للعملاء الموثوقين الذين يحتاجون جلسات Keith، ودورة
  حياته، والموافقات، والمخرجات، والأحداث المباشرة.

يمكن تشغيل الامتدادات كمكوّنات WASI بنطاق قدرات، أو كخوادم MCP، أو كمهارات،
أو كتطبيقات متّصلة تتطلّب موافقة. يمكن لعملاء ACP الاتصال عبر خادم stdio
المضمّن. راجع [توافقية OpenAI](docs/openai-compatibility.md) و
[تكامل المنصّة](docs/platform-integration.md).

## الأمان

> [!WARNING]
> يستطيع Keith تنفيذ الأوامر، وتعديل الملفات، والتحكم في متصفّح، واستدعاء
> خدمات خارجية بالصلاحيات التي تمنحها إياه. استخدم مساحة عمل يمكنك فحصها
> واستعادتها. عامل مخرجات النموذج، ورسائل القنوات، والصفحات المجلوبة،
> والإضافات، والمهارات، وخوادم MCP، ومرشّحي الإصلاح على أنها غير موثوقة.

أبقِ واجهة الويب وواجهات API على loopback ما لم تُضف TLS ومصادقة قوية
وسياسة شبكة صريحة. استخدم أسرارًا مختلفة لتسجيل الدخول إلى الويب،
ولواجهات API، ولمزوّدي النماذج، ولتوقيع الإصدارات. لا تنشر بيانات اعتماد
أو آثارًا غير منقّحة في issue عام.

أبلغ عن الثغرات بشكل خاص عبر
[نموذج security advisory](https://github.com/Sidiora-Labs/keith-agent/security/advisories/new)
على GitHub. اقرأ [SECURITY.md](SECURITY.md) لتعرف نموذج الثقة، والنطاق،
وقواعد الإبلاغ.

## النشر

يُسلَّم Keith كصورة OCI واحدة ذات حالة، مع مسارات مدعومة لـDocker Compose،
وKubernetes مع Helm، وRailway، وFly.io، وDigitalOcean Kubernetes، وAzure
Kubernetes Service، وAmazon EKS، وGoogle Kubernetes Engine Autopilot.

```bash
./keith deploy kubernetes --render
./keith deploy railway
./keith deploy fly --app my-keith
./keith deploy aws --cluster keith --region us-east-1
```

تطبع أوامر السحاب خطةً افتراضيًا. ولا يعدل النشر البنية التحتية إلا عند
تمرير `--execute` وضبط `KEITH_DEPLOY_APPROVED=YES`. اقرأ
[دليل النشر](docs/deployment.md) كاملًا قبل تعريض Keith خارج المضيف.

## التطوير والامتداد

أمر `./keith` هو نقطة دخول المساهم للإعداد، والخدمات المحلية، والفحوصات،
والاختبارات، وبُنى الإصدار، وصور الحاويات، والسقالات، وخطط النشر. تبقى مخرجات
بناء Rust خارج مجلد الـcheckout.

```bash
./keith check
./keith test
./keith image keith-agent:dev
./keith scaffold plugin my-plugin
./keith scaffold skill my-skill
```

يلزم توفر Rust 1.93 وNode.js 22.22 وCorepack وGit. قبل فتح pull request،
اقرأ [CONTRIBUTING.md](CONTRIBUTING.md) وأبلغ عن الأوامر والمسارات الفعلية
التي نفّذتها.
